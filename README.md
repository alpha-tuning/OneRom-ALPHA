# One ROM ALPHA

An ALPHA-focused firmware build for the open-source One ROM EEPROM replacement platform, with the goal of pushing it toward becoming one of the **world’s smallest and cheapest emulators**.

## What One ROM is

**One ROM** is an EEPROM replacement platform created by **Piers**. It was designed as a modern replacement for original EEPROM hardware, giving people a programmable alternative to older memory devices.

One of the biggest reasons this project matters is because **One ROM is open source**. That means the hardware and firmware foundation are available for people to study, build on, improve, and adapt. In a space where so much information has historically been locked away or treated like black magic, that matters.

That open-source foundation lines up heavily with what ALPHA stands for.

## What One ROM ALPHA is

**One ROM ALPHA** is my branch of that idea.

The goal is not just to make another EEPROM replacement. The goal is to push this platform into something much bigger for the Honda OBD1 world:

a **tiny**, **low-cost**, **open** emulator platform that gives more people access to real-time tuning hardware without the usual cost barrier.

Put simply, I am trying to turn an EEPROM replacement into what may become one of the **world’s smallest and cheapest emulators**.

The target is aggressive:

**$10 or less.**

That is a huge deal in a space where emulator hardware has traditionally been more expensive, more closed, and harder for the average person to get into.

## Why this matters

This project is about more than just cost.

It is about access.

It is about taking something that would normally be treated like a niche or protected tool and pushing it toward something more open, more understandable, and more available to the average builder, tuner, and enthusiast.

If this works the way I want it to, it helps lower the barrier to entry in a very real way.

That is what excites me about it.

## What we have coded into the ALPHA version so far

The ALPHA version of the firmware includes work aimed at shaping the platform toward emulator-style behavior and ALPHA-specific goals.

That includes custom work around:

- command handling
- communication behavior
- emulator-oriented firmware changes
- ALPHA-specific testing and experimentation
- compatibility work aimed at making the platform usable with existing tuning software

A major part of the current direction is making the device behave in a way that is **Ostrich-compatible from the software side**, so existing software can recognize it and communicate with it more easily.

That matters because compatibility helps get the hardware into people’s hands faster and lowers the amount of custom software support needed just to start using it.

## Ostrich compatibility and the bigger goal

Right now, part of the strategy is to make One ROM ALPHA behave as an **Ostrich-compatible emulator** from the point of view of the software.

That gives us a practical path forward using software that already exists and already understands that type of device.

But that is not the long-term dream.

The bigger goal would be to move beyond leaning on Ostrich-style compatibility and eventually see support for a **true One ROM-based protocol** that stands on its own.

That is something I would absolutely love to see happen with support from software developers.

In other words, Ostrich compatibility is the bridge.

A full **One ROM-native protocol** would be the destination.

## Open-source foundation

This project would not exist without **Piers** making One ROM open source.

That is the entire reason this branch is possible in the first place.

This is not about taking away from the original project. It is about building on a strong open foundation and pushing it in a direction that matches the ALPHA mission:

- lower cost
- smaller hardware
- open development
- less gatekeeping
- more real-world access

## Firmware release plan

The ALPHA firmware branch will be released once the YouTube video covering the project hits **1,000 views**.

And yes, that means we are dropping it **full of bugs or not**.

This project is still evolving. It is being tested, pushed, broken, improved, and figured out in real time. I would rather release something raw and real than pretend development only counts once it is polished.

If the community wants to see it, I want the community to be able to follow it.
